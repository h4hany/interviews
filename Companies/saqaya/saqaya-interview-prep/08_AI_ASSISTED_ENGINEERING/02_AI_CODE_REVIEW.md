# AI Code Review

## 1. Overview
The widespread use of AI coding assistants fundamentally changes the Code Review (PR Review) process. AI can write code much faster than a human can read it, leading to **reviewer fatigue**. Furthermore, AI makes specific types of mistakes that differ from human mistakes.

## 2. Reviewing AI-Generated Code: What to Look For

When reviewing code suspected or known to be AI-generated, focus on:
- **The "Looks Right" Trap:** AI code is syntactically flawless and often beautifully formatted. This lulls reviewers into a false sense of security. You must read for *semantic* correctness.
- **Edge Cases:** AI models are trained on the "happy path." They frequently omit null checks, timeout handling, and pagination logic.
- **Resource Leaks:** Check for unclosed database connections, missing file handle closures, or unmanaged Goroutines/threads.
- **Contextual Ignorance:** The AI doesn't know your database schema evolution or the quirks of your internal microservices. Check if the code makes false assumptions about internal systems.

## 3. Common AI Code Smells
1. **Zombie Code:** Dead code paths, unused imports, or variables that are initialized but never used (often leftovers from iterative prompting).
2. **Over-Engineering / Hallucinated Abstractions:** Generating 5 interfaces and 3 factory classes for a simple script because the AI mimicked Enterprise Java patterns for a Python script.
3. **Deprecated APIs:** Using a library version from 2021 because that was the model's knowledge cutoff.
4. **Schizophrenic Style:** The code switches between different paradigms (e.g., mixing functional `map/filter` with imperative `for` loops in the same file) because different prompts generated different blocks.

## 4. AI-Generated Test Quality
AI is excellent at generating tests, but terrible at generating *meaningful* tests.
- **Tautological Tests:** Tests that essentially assert `true == true`. For example, mocking a database call to return "X", and then asserting the function returns "X", without testing any business logic.
- **Missing Negative Cases:** AI rarely generates tests for malformed input, network failures, or race conditions unless explicitly prompted.
- **Actionable Standard:** Require engineers to use AI to generate Mutation Tests or Property-Based tests to prove the AI's standard unit tests actually catch bugs.

## 5. Establishing Code Review Standards for AI
As a Tech Lead, update your PR templates and guidelines:
- **Transparency:** If a complex algorithm was primarily generated by AI, the PR author should note it.
- **Smaller PRs:** Because AI increases code volume, enforce strict limits on PR size (e.g., max 300 lines of production code) to ensure reviewers can actually read it.
- **Automated Defenses:** Shift left. Use tools like SonarQube, Semgrep, or AI-powered review bots (like PR-Agent) to catch basic smells *before* a human looks at the PR.

## 6. Interview Questions

### Question 1: How do you adjust your code review practices now that your team uses AI coding assistants?
**What they are testing:** Awareness of AI-specific failure modes, process adaptation, reviewer fatigue management.
**Short Answer:** I shift focus from syntax and style (which AI does well) to architecture, business logic correctness, and edge cases. I also enforce smaller PRs to prevent reviewer burnout.
**Detailed Answer:** AI code often suffers from the "plausible bullshit" problem—it looks perfect but fails on edge cases. I train my team to look for "AI smells" like hallucinated dependencies or tautological unit tests. I also implement stricter automated linting and static analysis so human reviewers aren't wasting time on trivialities. Most importantly, I hold the author 100% accountable; "Copilot wrote it" is not a defense during a review. I expect the author to be able to explain the Big-O complexity and memory footprint of the generated code.
**Common Mistakes:** Saying "I use AI to review the AI code" without acknowledging the recursive risk of hallucinations.
**Strong TL Answer:** Mentions updating team culture (accountability), process (smaller PRs), and tooling (static analysis). Mentions the specific psychological trap of trusting well-formatted code.

### Question 2: You notice an engineer is submitting massive PRs very quickly, clearly generated by AI, and the quality is slipping. How do you address this?
**What they are testing:** Conflict resolution, performance management, coaching vs punishing.
**Strong TL Answer:** I would have a 1-on-1 with the engineer. I'd acknowledge their impressive speed and initiative in using AI tools, but pivot the conversation to the definition of done and the burden on reviewers. I'd explain that our bottleneck is no longer *writing* code, it's *verifying* and *maintaining* it. We would agree on actionable constraints: breaking tasks into smaller PRs (under 400 lines), and requiring them to walk me through the execution flow of the next few PRs synchronously. The goal is to calibrate their standard of quality to match their new speed.
